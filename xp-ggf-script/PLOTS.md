# Plot Guide

This document explains the PNG plots produced in `xp-ggf-script/out/`.

If a run uses `--http-latency-ms`, that artificial per-call latency is included
in the script-side wall time shown in the plots.

Important scope note:

- the plots described here are generated by the benchmark runner
- the standalone SHACL validation queries under `queries/` are not part of these benchmark plots yet

There are currently two different plot families in this experiment.

## 1. Per-run Comparison Plot

Produced by:

- `xp-ggf-script/evaluate_ggf_vs_script.py`

Default output:

- `xp-ggf-script/out/ggf_vs_script_eval.png`

Examples:

- `xp-ggf-script/out/metaqa_entity_similarity_50.png`
- `xp-ggf-script/out/metaqa_local_schema_eval.png`
- `xp-ggf-script/out/metaqa_random_sample_eval.png`
- `xp-ggf-script/out/final_http_eval_100q_rerun.png`

Important:

- `metaqa_local_schema_eval.png` is generated from the runner case `local_schema`
- this case now uses `--schema-hops 2` by default
- this is different from the generic runner option `--hops`, which is used by other cases

### What is inside

This PNG now has **four panels**.

Top-left:

- title: `Transfer by case (log scale)`
- y-axis: `Transferred bytes`
- bars:
  - `GGF`
  - `Script`

Top-right:

- title: `Calls by case (log scale)`
- y-axis: `Logical calls`
- bars:
  - `GGF`
  - `Script`

Bottom-left:

- title: `Transfer ratio (log scale)`
- y-axis: `Script / GGF transfer ratio`
- bars:
  - one bar per case

Bottom-right:

- title: `Wall time by case (log scale)`
- y-axis: `Wall time (s)`
- bars:
  - `GGF`
  - `Script`

### What one x-axis label means

Each x-axis label is one benchmark case, for example:

- `expand`
- `paths`
- `random_sample`
- `entity_similarity_compare`

If you run only one case:

- each panel shows just one case

If you run several cases:

- each panel shows one group or one ratio bar per case

### What the top-left panel means

`Transferred bytes` is the total transfer metric used by the benchmark.

For `GGF`, this is typically:

- query input bytes
- plus compact result bytes

For `script`, this is typically:

- in `--script-access http` mode, HTTP request bytes sent to the local SPARQL endpoint
- plus HTTP response bytes returned by that endpoint
- plus normalized result bytes
- in `--script-access local` mode, the older approximation based on locally materialized graph bytes

So this panel is about **data movement / transfer cost**, not semantic quality.

### What the top-right panel means

`Logical calls` counts the number of high-level calls made by each side.

Examples:

- in `--script-access http` mode, this is the number of HTTP SPARQL requests emitted by the script baseline
- many scripted loops may therefore increase the script call count
- some `GGF` cases use a single compact query
- `random_sample` is now counted as `1` GGF call in the runner
- the `random_sample` script baseline uses a more granular HTTP orchestration
  - predicate discovery
  - then per-predicate triple retrieval

So this panel is about **orchestration complexity**, not runtime.

### What the bottom-left panel means

This panel shows how many times more data the script side transfers compared with GGF.

Examples:

- `1x` means both sides transfer about the same volume
- `10x` means the script transfers about ten times more
- very large values are easier to read here than on the absolute transfer chart

### What the bottom-right panel means

This panel shows the measured wall-clock time per case.

It is also plotted on a log scale so that:

- fast local cases are still visible
- slower cases such as `simrank` or `metaqa_2hop_local` do not flatten the others

For the benchmark runner, the GGF side now uses CLI preloading via `--load`, and its reported wall time excludes the TTL parsing step. So the GGF bar here is intended to represent execution time of the graph query itself, not dataset loading overhead.

If `--http-latency-ms` is used, the script wall-time bar also includes that
fixed artificial latency once per HTTP SPARQL call. This is useful when the
script baseline would otherwise benefit too much from localhost conditions.

### What this plot does not show

This plot does **not** show:

- recall / accuracy
- cardinality error
- per-predicate estimation details
- SHACL validation results

Those values are available in:

- the JSON output
- the CSV summary

In particular, `random_sample` cardinality metrics are in:

- `exact_cardinality`
- `estimated_cardinality`
- `cardinality_absolute_error`
- `cardinality_relative_error`

But they are **not plotted** in this PNG for now.

## 2. MetaQA Scaling Summary Plot

Produced by:

- `xp-ggf-script/plot_metaqa_scaling_summary.py`

Default output:

- `xp-ggf-script/out/metaqa_scaling_summary.png`

This script reads several benchmark JSON files and summarizes them as a scaling curve.

### Intended usage

This plot is mainly for **MetaQA scaling experiments** where you compare several runs with different sizes.

Typical example:

- one JSON for 20 questions
- one JSON for 50 questions
- one JSON for 100 questions

### What is inside

This PNG has **two line plots**.

Left panel:

- title: `Execution time`
- x-axis: `Usable questions`
- y-axis: `Wall time (s)`
- lines:
  - `GGF`
  - `Script`

Right panel:

- title: `Transfer volume`
- x-axis: `Usable questions`
- y-axis: `Transferred data (MB)`
- lines:
  - `GGF`
  - `Script`

On the right panel, the script also annotates each point with:

- `R=...`

This is the average gold recall extracted from the JSON summary.

### Important limitation

`plot_metaqa_scaling_summary.py` assumes each input JSON corresponds to one main run summary and currently reads:

- `payload["summary_rows"][0]`
- `payload["results"][0]["ggf"]["normalized_output"]`

So it is best suited to:

- single-case scaling runs
- especially MetaQA QA-style runs

It is **not** the right plotter for a multi-case comparison like:

- `expand paths simrank`
- `all`

For that, use the per-run comparison plot from `evaluate_ggf_vs_script.py`.

## Which plot should I read?

Use `evaluate_ggf_vs_script.py` PNG when you want:

- transfer comparison by case
- logical call comparison by case
- one compact figure for one benchmark run

Use `plot_metaqa_scaling_summary.py` PNG when you want:

- scaling curves across several JSON runs
- wall time vs dataset size / question count
- transfer volume vs dataset size / question count

## Quick Examples

Single run with several cases:

```bash
python xp-ggf-script/evaluate_ggf_vs_script.py \
  --config config.ini \
  --cases expand simrank random_sample local_schema
```

This produces one PNG with:

- top-left: transfer bytes per case
- top-right: logical calls per case
- bottom-left: transfer ratio per case
- bottom-right: wall time per case

Scaling summary from several JSON files:

```bash
python xp-ggf-script/plot_metaqa_scaling_summary.py \
  --inputs xp-ggf-script/out/metaqa_20.json xp-ggf-script/out/metaqa_50.json
```

This produces one PNG with:

- left: execution time curve
- right: transfer volume curve

## Current Gap

At the moment, there is no dedicated PNG for:

- cardinality estimation error
- per-predicate estimation error

Those values exist in the `random_sample` JSON/CSV outputs, but they are not visualized yet.

If needed, a next step would be to add a third plot family for:

- exact vs estimated cardinality
- absolute / relative error
- error by predicate
